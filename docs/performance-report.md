# 성능 리포트 (단계 7)

목표(PRD 7장): 입력에서 화면 반영까지 16ms(60fps) 이내, A4 150DPI에서 끊김 없음.

## 어떻게 쟀나

- 빌드한 앱(`npm run build` + `vite preview`)을 이 컴퓨터의 브라우저에서 실행했다.
- 새 A4 그림(1240×1754px, 150DPI), **레이어 3장**을 만들고 도구마다 "펜 압력이 변하는 곡선 한 획(이동 이벤트 100번)"을 그렸다.
- 이 앱은 이동 이벤트 안에서 바로 그리므로(프레임으로 미루지 않음), 이벤트 처리 시간이 곧 그리는 데 걸리는 시간이다. 한 이벤트당 걸린 시간의 **중앙값 / 95번째 백분위 / 최댓값**을 적는다.
- 브러시 크기는 각 도구의 기본값이다(따로 적은 경우 제외).

## 결과

### 선·붓·도형 도구 (문제 없음)

| 도구 | 중앙값 | 95% | 최대 |
| --- | --- | --- | --- |
| 볼펜, 만년필, 연필, 붓펜 | 0.0~0.1ms | 0.1~0.4ms | 0.2~6ms |
| 형광펜, 수채 붓, 유화 붓, 크레용, 에어브러시, 목탄, 텍스처 붓, 지우개 | 0.0~0.1ms | 0.1~0.3ms | 0.2~0.8ms |
| 사각형, 원/타원, 곡선(미리보기 도형) | 0.1ms | 0.3~0.4ms | 1.7~2.2ms |

손을 뗄 때 한 번에 그리는 도구는 형광펜 6ms, 그라데이션 채우기 54ms가 걸린다(한 번뿐이라 끊김으로 느껴지지 않는다).

### 픽셀을 읽는 도구 (느렸던 곳 → 고침)

번짐·블러·리터치·물 번짐 같은 도구는 도장을 찍을 때마다 그림 조각을 읽어 계산한다. 획 하나에 도장이 수십 개 찍히는데, 도장마다 큰 배열을 새로 만들고 픽셀마다 `Math.hypot`을 부르고 있었다.

**고친 내용**(`src/tools/engines/pixel.ts`): 작업 배열을 재사용하고, 세기 표를 도장당 한 번만 계산하고, 블러의 경계 계산을 단순하게 했다. 결과 픽셀은 같은 규칙으로 계산한다(도구 테스트 139개 통과).

| 도구 | 고치기 전 중앙값 (95% / 최대) | 고친 뒤 중앙값 (95% / 최대) |
| --- | --- | --- |
| 번짐 도구 | 37.9 (95.6 / 116) | **2.7** (9.3 / 17.3) |
| 블러 | 14.6 (37 / 48.9) | **2.9** (7 / 9.9) |
| 물 번짐 | 29.3 (63 / 72.6) | **6.1** (13.1 / 14.1) |
| 색 번짐 보정 | 14.1 (30.9 / 34.7) | **1.8** (5.3 / 11.6) |
| 리터치 손가락 | 83.1 (172 / 241) | **2.5** (8.8 / 30) |
| 선명하게 | 15.2 (36.1 / 44.7) | **3.0** (7.7 / 9.0) |
| 색 지우개 | 18.0 (43.5 / 56) | **1.0** (3.0 / 10.9) |

단위는 ms. 기본 크기에서는 중앙값·95%가 모두 16ms 안이다.

### 실제 프레임 간격 측정 (Edge, 폰 화면 412×915, A4·레이어 3장)

화면에 보이는 브라우저(Edge, 스크립트로 조종)에서 입력을 프레임마다 한 번씩(60Hz처럼) 보내고 프레임 사이 시간을 쟀다. 16.7ms면 60fps다.

**이 컴퓨터 속도 그대로 (그래픽 카드 없이 CPU로 그리는 설정)**

| 도구 | 프레임 간격 중앙 / 95% | 놓친 프레임(25ms 초과) / 90 |
| --- | --- | --- |
| 볼펜, 만년필, 수채 붓, 크레용, 에어브러시, 지우개 | 16.6~16.7 / 17~20ms | 0~3 |
| 번짐 도구, 블러, 리터치 손가락 | 16.6~16.7 / 18ms | 0~1 |
| 물 번짐 | 17.2 / 21.5ms | 1 |
| **형광펜** | **18.8 / 30.9ms** | **6** |

거의 모든 도구가 60fps다. 형광펜(임시 층에 그렸다가 합치는 방식)만 프레임을 조금 놓친다.

**CPU를 4배 느리게 한 시험 (중간 사양 폰을 흉내 낸 것, 정확하지 않은 대략치)**

| 도구 | 프레임 간격 중앙 | 그리기 처리 시간 중앙 |
| --- | --- | --- |
| 볼펜, 만년필 | 약 90~105ms (약 10fps) | 7ms |
| 수채 붓, 크레용, 형광펜, 에어브러시, 지우개 | 약 30~190ms | 6~16ms |
| 번짐 도구, 블러, 리터치, 물 번짐 | 약 90~270ms | 60~170ms |

→ **CPU가 4배 느린 기기에서는 60fps를 못 낸다.** 이 시험은 그래픽 가속이 없는 환경이라 실제 폰(그래픽 가속 있음)보다 나쁘게 나올 수 있고, 첫 도구는 워밍업 때문에 더 느리게 나오는 등 값이 흔들린다. 그래서 "중간 사양 폰에서 끊김 없음"은 **확인하지 못했고, 지금 숫자로는 보장할 수 없다.**

**병목 분석 (프로파일링)**: 4배 느린 조건에서 프레임당 약 114ms 중 대부분이 그리기 코드(약 8ms)가 아니라 **화면 그리기(Paint)**였다. 원인은 그림 캔버스가 큰 데다(A4 1240×1754px, 레이어마다 한 장) 번짐·채우기 같은 픽셀 도구 때문에 CPU 캔버스(`willReadFrequently`)로 만들어서, 획을 그릴 때마다 바뀐 캔버스 전체를 화면에 다시 올리기 때문이다.
- 시도한 것: 캔버스마다 별도 합성 층으로 분리(`will-change: transform`), 종이 전체를 한 층으로 분리, 둘 다. → **효과 없음**(프레임 간격 93~111ms 그대로)이라 적용하지 않았다.
- 제대로 고치려면: 그리는 동안의 획을 **화면 크기의 작은 캔버스**에 먼저 그리고 손을 뗄 때 레이어에 합치는 구조로 바꿔야 한다(큰 변경). 또는 브러시 도구는 그래픽 가속 캔버스, 픽셀 읽는 도구만 CPU 캔버스로 나누는 방법이 있다. 이번 출시 범위를 넘어서 하지 않았다. **폰에서 실제로 끊기는지 먼저 확인한 뒤** 필요하면 진행한다(점검표 C).

### 남은 느린 곳 (알려진 한계)

- **큰 브러시의 픽셀 도구**: 번짐 도구 두께 200(최대)에서 처리 시간 중앙 11.8ms / 95% 25.8ms, 블러 두께 200에서 중앙 20.1ms / 95% 47.7ms. 큰 붓으로 아주 빠르게 문지르면 프레임이 몇 번 건너뛸 수 있다.
- **큰 영역 채우기**: 페인트 통은 B2(약 2950×4170px) 전체를 한 번에 채우는 데 약 0.65초, 이를 되돌리기·다시하기 하면 다시 그리느라 약 0.8초가 걸린다.
- **형광펜**: 위 표처럼 보통 속도에서도 프레임을 조금 놓친다.

## 재지 못한 것 (직접 확인이 필요함)

- **실제 스마트폰·태블릿·펜**: 한 번도 재지 못했다(그래픽 가속 있는 실제 기기의 프레임은 위 시험과 다를 수 있다). 출시 전 점검표(`docs/store/release-checklist.md`)에 실제 기기에서 확인할 항목을 넣었다.
- 폰에서 끊기면 먼저 볼 곳: 레이어 수 줄이기, 큰 붓 크기 줄이기, 용지를 A4 이하로 쓰기.
